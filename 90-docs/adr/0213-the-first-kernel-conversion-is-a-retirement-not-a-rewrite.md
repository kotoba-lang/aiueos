# ADR-0213 — the first kernel conversion is a retirement, not a rewrite

- Status: accepted
- Date: 2026-09-10
- Related: ADR-0212 (conversion order), ADR-0013 (C-free hard-flip rule)

## Context

ADR-0212 measured the conversion order and named `relay_protocol.c` (63 lines,
layer 0, no pointer walking, every primitive confirmed present) as the first
kernel file to convert to Kotoba. Converting it turned out not to mean writing
Kotoba.

## It is already written

`os/aiueos/native/relay_line.kotoba` exports
`store-byte store-template store-hex store-dec store-mac-hex …` — precisely
what `relay_protocol.c`'s `append_text` / `append_hex64` / `append_mac` are —
and `os/aiueos/native/relay_text.kotoba` carries the line skeletons as packed
i64 words. The Kotoba side is the better of the two: it is generated by
`tools/gen-relay-text.cljs`, which checks every template against the relay's
own regexes in `tools/k16-pxe-server.py`, so a protocol change on the Mac makes
the file fail to regenerate rather than making the board transmit a line
nothing accepts. The C has no equivalent check.

**Both are live.** `build-uefi.sh` compiles `relay_protocol.c` into the kernel
and links it; `pci.c:4038` and `pci.c:4109` call it. `debug_link.kotoba` and
`kotoba/murakumo-join-plan.kotoba` use the Kotoba pair. Two implementations of
one wire protocol, in one image.

## They are the same bytes

Measured, not inspected. The C, built standalone (it is layer 0, so it links
with nothing else) with nonce `0x0123456789abcdef` and MAC `70:70:fc:0b:b6:31`:

    91 bytes  "AIUEOS_NODE_HELLO_V1 boot=0123456789abcdef mac=70-70-fc-0b-b6-31 profile=rtl8125-relay-test"

The Kotoba template for kind 0, decoded from its twelve i64 words:

    91 bytes  "AIUEOS_NODE_HELLO_V1 boot=0000000000000000 mac=00000000000000000 profile=rtl8125-relay-test"

Identical outside the two variable spans the skeleton leaves as `'0'`
(`boot=` at 26..41, `mac=` at 47..63). Same length, same banner, same
separators, same suffix, same field offsets.

`os/aiueos/scripts/relay-protocol-c-kotoba-parity.cljs` is that comparison as a
gate, registered as `:relay-parity`. It proves its own discrimination on every
run: flipping one byte of the fixed `profile=` suffix must make it disagree,
and changing a byte inside `boot=` must not.

## Decision

**The first kernel conversion is a retirement.** `relay_protocol.c` is deleted
when `pci.c` stops calling it — not rewritten in Kotoba, because the Kotoba
already exists and is better attested. Until then the parity gate stands as a
drift alarm: edit either side alone and it goes red.

This changes what ADR-0212's ordering means. The order is right, but "convert"
is the wrong verb for at least some entries: before writing Kotoba for a C
file, look in `os/aiueos/native` for the module that already does it. The
question for each file is which of three it is:

1. **already in Kotoba, C is a duplicate** → retire the C (this file)
2. **not in Kotoba, expressible** → write it
3. **not in Kotoba, blocked** → record blocked (ADR-0212's 840 lines)

Nothing in ADR-0212 distinguished 1 from 2, and it should have: `relay_protocol.c`
was its top recommendation.

## What is not done

`pci.c` still calls the C, so nothing is deleted here. `pci.c` is layer 6 of
eight, 5,482 lines, 16 dependencies — the second-to-last file in the order — so
this retirement waits on nearly the whole conversion, or on linking the Kotoba
object into the C build ahead of that. Which of those is cheaper is not measured.

The parity gate covers the HELLO line. `aiueos_relay_ack_payload` and
`aiueos_relay_ack_payload_valid` are not yet compared against a Kotoba
counterpart; the ACK template is not among the seven kinds `relay_text.kotoba`
generates, so that comparison has nothing to run against yet.
